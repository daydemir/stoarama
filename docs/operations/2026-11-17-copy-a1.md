# A1: bounded COPY control and per-item custody blocks

Future client literal: `r2-copy-v4`, built by the existing
`NAS_VERSION=r2-copy-v4 backend/scripts/release-nas-pull.sh` flow. Source retains
its `development` placeholder. Release is exclusively controller-owned after
merge, backend deployment/migration review, COPY drain and exact artifact binding.
Merge uses `[skip render]`; it grants no production action.

Migration `0200_nas_r2_copy_progress.sql` is additive. Existing reviewed COPY
clients, including `v85r-nas-proof-v2.2`, remain eligible; old results have blank
completion and zero newly reported committed bytes. Their historical verified
rows are not guessed into either completion category. New completed range
checkpoints accumulate bytes durably, once per range id, including old clients.
The v4 cleanup executor retains v2.2's single-item execution group. No stitch
producer/reader profile or proof admission is added for v4.

Each worker owns one control child with a 15-second startup bound and a separate
2-second request total. The child reuses its origin-bound HTTP/1.1 TLS connection,
consumes bounded error bodies, refuses redirects and disables automatic connect
inside POST send. A dead idle connection may be replaced before send; send/read
failures kill and reap the child and never replay that POST.

Client deterministic conflicts are journaled in `/state` inventory SQLite
`r2_copy_blocks` before network reporting. Typed reasons are `final_conflict`,
`sidecar_conflict`, `partial_conflict`, `path_conflict`, `checksum_mismatch`.
The block endpoint requires the item's owning token; expired-but-unreassigned
owners may report, reassigned tokens may not. Reporting has no disk/memory floor,
source revalidation or maintenance gate. Lost reports retain local evidence and
are reported again if the item is re-leased; a local mismatch is visible in the
heartbeat even before the server acknowledges it. No automatic reconciliation
clears either latch. Media and conflicting sidecars/partials are preserved.

The server blocks changed catalog identity (`source_changed`), missing R2 objects
and successful HEAD responses with wrong identity (`r2_identity`). Provider or
transport HEAD errors return a visible retryable 503. An acknowledged block
immediately advances the client. Resource holds remain resumable and all control
HTTP refusals are visible in logs.

The durable predicate for B1/B2 is `nas_r2_copy_items.state='blocked'`, exact key
from `item->>'bucket'` / `item->>'object_key'`, reason in `blocked_reason`.
`checksum_mismatch` and `final_conflict` form the per-item mismatch latch. Existing
inventory never overrides it. The DB reservation trigger also vetoes pending and
leased COPY keys. COPY import and independently committed reservation publication share an exact
key advisory lock. The outer retirement transaction keeps its existing global
fence; the reservation connection never reacquires it. Existing retirement
intent prevents new COPY admission.
A blocked row cannot be cleared, deleted or rebound by ordinary SQL or manifest
reimport. This does not stop unrelated non-keep28 work.

## Controller telemetry

`stoaramactl nas-r2-copy status --json` emits one JSON document:

- `schema`: `stoarama.nas-r2-copy-status.v1`; `updated_at`: UTC snapshot time.
- `queue_depth`: pending + leased rows; `blocked`: all blocked rows.
- `verified_in_place`, `downloaded`: each `{objects,bytes}` from verified rows.
  Downloaded means a new final was published in that execution, including a
  complete resumed partial; it is not a claim that all its bytes crossed R2 now.
- `verified_in_place_items_per_minute`, `downloaded_items_per_minute`: separate
  completed-item counts in the last rolling 60 seconds, based on server
  `verified_at`; these are rates, not lifetime averages.
- `downloaded_bytes`: durable sum of successfully completed range checkpoints;
  an interrupted range or a lost completion report is not counted.
- `committed_bytes`: final file sizes in successful v4 result reports.
- `blocked_by_reason`: reason → `{objects,bytes}`; `mismatch_latched`: count of
  checksum/final conflicts. These aggregates survive restart and exact reimport.
- `attempts`, `re_leased_items` (attempts > 1), `max_attempts`: persistent queue
  churn diagnostics; inspect `id,attempts,updated_at,last_error` for item detail.

Actual client transfer/publication counters, including work before a failed
result report, and resource holds are at heartbeat `cleanup.r2_copy`, stored in
`connections.nas_cleanup_status->'r2_copy'`, with freshness from
`nas_cleanup_status_at` and identity from the ordinary heartbeat boot id.
`holds_by_reason`, `downloaded_bytes`, `committed_bytes`, `verified_in_place`
are boot-scoped; `mismatch_latched` counts durable local checksum/final conflicts.
Controller stop checks must inspect both local and server latches; neither is
permission to stop unrelated non-keep28 deletion. Block reason counters include
sidecar conflicts; all HTTP holds use `http_<status>`.

First-hour checks: verified-in-place > 0; no sidecar conflicts; mismatch latches
zero; roughly ≥400 verify-in-place items/min with resource holds <20%; startup READY distribution and
request SENT/status distribution separately; no repeatedly re-leased lowest row;
blocked keys remain protected and unrelated rows progress. Keep existing memory,
load and free-space floors unchanged. Cleanup runs only on the controller's
free-space hold decision. Collated, checkpoint folding and reverify are separate.
